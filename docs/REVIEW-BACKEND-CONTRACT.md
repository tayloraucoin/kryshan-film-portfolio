# Review backend contract

The client review layer (`/review/*` in every client site) reports to tayloraucoin.com. This file is the contract between the two codebases.

**Canonical home:** this file, in `client-boilerplate`. The taylor-aucoin repo keeps a copy at `docs/review/REVIEW-BACKEND-CONTRACT.md` and must match it. Change this one first, then the copy, then both implementations.

## 1. Transport

|          |                                                                                                                                                                                                       |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Base URL | `REVIEW_BACKEND_URL` in the client site's env (for example `https://tayloraucoin.com`). Every path below is relative to it.                                                                           |
| Auth     | `Authorization: Bearer <key>`. One key per review round, minted in taylor-aucoin by `yarn review:create`, shown once, stored only as a SHA-256 hash. The client site holds it as `REVIEW_INGEST_KEY`. |
| Caller   | The client site's **server** (server actions in `app/review/_actions/`). The key never reaches a browser, so there is no CORS and no origin check.                                                    |
| Encoding | JSON both ways. `Content-Type: application/json`. Request bodies over 64 KB are refused.                                                                                                              |
| Timeouts | The client waits 8 seconds, then treats the call as failed. Failed writes are kept in the reviewer's browser and retried with the **same id**, so every write must be idempotent on `id`.             |

## 2. Errors

| Status | Body                          | When                                                                   |
| ------ | ----------------------------- | ---------------------------------------------------------------------- |
| 401    | `{ "error": "unauthorized" }` | Missing, malformed, or unknown key. No distinction between the three.  |
| 400    | `{ "error": "bad_request" }`  | Body fails validation.                                                 |
| 405    | `{ "error": "method" }`       | Wrong method.                                                          |
| 500    | `{ "error": "server" }`       | Anything else. Logged with an id and a count, never with comment text. |

Every success is `200` with `{ "ok": true, ... }`.

## 3. Endpoints

### `GET /api/review/health`

Proves the key resolves and tells the review index what round it is talking to.

```json
{
  "ok": true,
  "round": {
    "label": "Phase 1 · kits and layouts",
    "clientName": "Client Name",
    "submittedAt": null
  }
}
```

### `GET /api/review/comments?path=<path>`

Lists live comments. `path` is optional; without it every comment in the round is returned. Soft-deleted comments are excluded. Sorted by `createdAt` ascending.

```json
{ "ok": true, "comments": [ ReviewComment ] }
```

### `POST /api/review/comments`

Body: `ReviewComment`. Idempotent on `id`: a second POST with an existing id returns `200 { "ok": true }` and changes nothing.

### `DELETE /api/review/comments/<id>`

Soft-deletes (sets `deleted_at`). An unknown id also returns `200 { "ok": true }` so a retry after a lost response cannot fail.

### `POST /api/review/submissions`

Body: `ReviewSubmission`. Idempotent on `id`. On first receipt the backend stamps the round's `submitted_at` and emails Taylor a plain-text summary (existing `notifyOps` rail). A round stays open for comments after submission.

## 4. Shapes

```ts
type ReviewComment = {
  id: string; // uuid, generated by the client site so retries are idempotent
  path: string; // the page it was left on, e.g. "/review/mocks/kit-a"; ≤ 512 chars, starts with "/"
  body: string; // 1..4000 chars, trimmed
  target: {
    selector: string; // CSS selector the client site can resolve again; ≤ 1024 chars
    x: number; // 0..1, horizontal position inside the target's box
    y: number; // 0..1, vertical position inside the target's box
    label?: string; // human-readable name of the element, e.g. "Hero headline"; ≤ 200 chars
  };
  viewport: { width: number; height: number }; // integers; the reviewer's viewport when they clicked
  createdAt: string; // ISO 8601, set by the client site
};

type ReviewSubmission = {
  id: string; // uuid
  preferredKit: string | null; // kit id from the client site's registry, e.g. "kit-a"
  preferredLayout: string | null; // layout id
  preferredMock: string | null; // mock id
  flinch: string | null; // "what made you flinch", ≤ 5000
  fightFor: string | null; // "anything you'd fight for", ≤ 5000
  notes: string | null; // anything else, ≤ 5000
  commentCount: number; // integer; how many live comments the client site counted at submit time
  submittedAt: string; // ISO 8601
};
```

Both shapes are validated with zod on both sides. The zod schemas live at `lib/validators/review.ts` in each repo and must agree field for field.

## 5. Storage (taylor-aucoin)

Three tables, deny-all RLS like every other table there:

- `review_rounds` — one per client review round: `id`, `created_at`, `updated_at`, `client_name`, `label`, `engagement_id` (nullable, `on delete set null`), `key_hash` (unique), `site_url` (nullable), `submitted_at` (nullable).
- `review_comments` — `id` (client-supplied uuid, primary key), `round_id` (cascade), `created_at`, `client_created_at`, `deleted_at`, `path`, `target` (jsonb), `body`, `viewport_width`, `viewport_height`.
- `review_submissions` — `id` (client-supplied uuid, primary key), `round_id` (cascade), `created_at`, `payload` (jsonb: the full `ReviewSubmission`).

## 6. What is deliberately not here

- No browser-side calls. If a future surface needs them, add CORS and a separate public token; do not expose the ingest key.
- No admin UI for reading results. Taylor reads the email and, for now, the table. Roadmap.
- No rate limiting. The key is the gate; a leaked key is rotated by minting a new round.
- No editing of comments. Delete and re-add.
